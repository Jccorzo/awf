# Phases

Every instant of a session belongs to exactly one phase, so phase times add up to the session's total. Phases come from PLAN.md; don't add one without asking. The rules that decide them live in [src/classify/default-rules.yaml](../src/classify/default-rules.yaml), and a repo can extend them in `.awf/rules.yaml`.

| Lint and format        | eslint, prettier, biome, ruff, black, isort, flake8, mypy, pyright, golangci-lint, gofmt, go vet, cargo clippy, cargo fmt, ktlint, detekt, swiftlint, swiftformat, dotnet format, `tsc --noEmit`, stylelint, shellcheck, rubocop, dart analyze, flutter analyze, dart format, dart fix, custom_lint, dcm                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

| Build                  | tsc, tsc-alias, vite build, webpack, esbuild, next build, go build, cargo build, gradle assemble, mvn package, dotnet build, msbuild, xcodebuild build, swift build, bazel build, make, cmake --build, docker build, flutter build, dart compile, build_runner. | Running scripts        | Running something that isn't a check, an edit or a read, and the model time before it: scripts (`python3`, `node`, `bash`, a script run by its path), the app and its dev servers, HTTP calls (`curl`), databases (`psql`), containers and clusters, cloud CLIs and deploys, publishing, `git push`, `gh pr create` and other CI actions, other agents run from the shell (`claude -p`), and polling loops, watching CI included (`gh run watch`, `gh pr checks --watch`). ## Attribution rules

1. **Model time goes to the phase of the tool call it produced.** When one stretch of model time produced several calls (a batch), it takes the highest-ranked of their phases, in the order of "Overlaps and waiting" below: writing an edit outranks running a script, since the model's time went into the edit. Model time before a question to you, a subagent or nothing at all is Planning and answering.
2. **A compound command takes the highest-ranked phase**, in the order Build, Running tests, Lint and format, Running scripts, Writing tests, Writing code, Exploring. The other phases stay as tags. `npm run lint && npm test` is Running tests, tagged Lint and format. Commands that change nothing (`cd`, `echo`, `export`, `sleep`, `kill`, `true`, `open`) don't count; a command made only of them is Unclassified.
   - **Running something takes the time.** Edits and reads in a shell take next to no time, so in `mkdir -p out && python3 gen.py` the script most likely took it: the command is Running scripts, not Writing code. `python3 gen.py && pnpm test` is still Running tests.
   - **A part no rule matches** ranks above Running scripts, below the checks: it could be anything, so `python3 gen.py && frobnicate` is Unclassified.
   - **A filter after a pipe** (`| tail`, `| grep`, `| jq`) decides nothing unless it is a check or writes files: `pnpm test | tail` is Running tests, `some-cli | tail` is Unclassified.
   - **Polling** (a `sleep` inside a `while`/`until`/`for` loop, or a sleep of 5 seconds or more) is Running scripts, tagged `polling`, unless the command also runs a check: the time went to waiting for something outside the session, like CI, a deploy or a server starting. The summary says how much of Running scripts was polling.
   - Calls of shell functions defined in the same command (in a substitution too, and inside an `if`), and `case` patterns, are skipped; the function's body is counted once. A function that runs its arguments (`run() { name=$1; shift; "$@" > "$name.log"; }`, `ci() { env CI=true "$@"; }`) runs them where it's called: `run lint pnpm lint` is Lint and format, after the arguments its body shifts off (a `shift` that may not run, after a test or in an `if`, a `case` or a loop, isn't counted), behind a wrapper too (`time run …`). When the body pipes them or follows them with `||` (`"$@" | tail`), their exit code isn't trusted. A shell script that does (`exec "$@"`, an env wrapper, a dispatcher ending in `"$@"`) runs the arguments it was called with the same way, a function of its own by its body. An array's values (`ARGS=(-a "$b")`) aren't commands.
   - **A variable run as a command** (`G="git -C ../x"; $G status`, `"$CHROME" --headless`) runs what it was set to earlier in the same command, after a wrapper too (`caffeinate -i $G pnpm test`), and so does an array (`G=(gcloud --project p); "${G[@]}" run deploy`). `time` before a subshell or a group (`time (cargo test)`, `time { cargo test; }`) or before assignments (`time CI=1 pnpm test`) times what follows it, and `taskpolicy`, like `nice`, runs its command. A value from a command substitution (`T=$(cat tool)`) isn't known.
   - **Commands inside a substitution count**: `OUT=$(pnpm test 2>&1); echo "$OUT" | tail` is Running tests, and so is `diff <(git show HEAD:a.ts) a.ts`'s `git show`. A `cd` inside parentheses ends with the subshell.
   - **Browser and computer-use calls** are classified by what they do, from the action names in their input. Looking at a page or the screen (`navigate`, a screenshot, `zoom`, scrolling, `get_page_text`, `find`, console and network logs) is Exploring; acting on it (clicks, typing, `javascript_tool`, `preview_start`) is Running scripts. A batch (`browser_batch`, computer use's `computer_batch`) takes the highest-ranked of its calls, so a batch that clicks is Running scripts and one that only loads a page and takes a screenshot is Exploring. Waiting for the page (`wait`) doesn't count next to other calls; a call that only waits is polling.
   - **Other MCP tools** are classified by their name. One named for reading (`get_`, `list_`, `search_`, `read_`, `fetch_`, `find_`, `describe_`, with `-` too as in `get-library-docs`, also Slack's `slack_read_` and Notion's `notion-fetch`, and `whoami`) is Exploring, from any server; `find_and_replace` isn't, and neither is a `query`, which can write, as `psql` does. Figma's `create_session`, which it opens before reading or writing, is Exploring too, and its other calls (`use_figma`, `generate_*`, `create_*`, `download_assets`) are Running scripts. In the Claude Code desktop app, starting, stopping or archiving another session is Running scripts, like `claude -p`, and messaging one or marking a chapter is Planning and answering. A command run in a terminal tab (`mcp__terminal__run_in_terminal`) and publishing an Artifact are Running scripts; `ScheduleWakeup` and `CronCreate` are planning. One named for acting (`send_`, `create_`, `update_`, `delete_`, `post_`, `upload_`, `bind_`, `show_`, `batch`) is Running scripts, from any server. The desktop app asking you for a folder, to keep the machine awake or to discard a kept worktree is Waiting on you. A tool named for neither (`find_and_replace`, `query`) stays Unclassified.
   - **Commands that run other commands** are classified by what they run: `hushrun run -- pnpm test`, and `hushrun run test` and `hushrun run --stage staging` by the checks they run, each by its `run` in `hushrun.yaml` or else its name (hushrun's `ready`, `status`, `plan`, `digest` and `hook pre-push` only report: Exploring; `init`, `hook install` and signing in are Running scripts), `script -q /dev/null cmd` and `script -c "cmd"` (which give a command a terminal), `find … -exec black {} +`, `run-s lint test`, `concurrently "npm:test"`, task runners (`just test`, `task lint`, `mise run build`, `rake spec`, `composer test`) by the task's name, and `melos exec -- flutter test` by the command it runs in each package.
3. **Scripts are resolved to what they actually run before classifying**: `npm run <script>` and its `pnpm`, `yarn` and `bun` forms (with their `pre` and `post` scripts), `make <target>` (the target's own recipe; an empty one runs its prerequisites), Gradle tasks and Maven goals (by task name), melos scripts (`melos run <script>` and `melos <script>`, from `melos.yaml` or the `melos:` section of the workspace's `pubspec.yaml`, following their `steps`), a dependency's executable run with `dart run <package>` or `dart pub global run <package>`, as `npx` runs one (`dart run build_runner build` is build_runner's build; the package's own executable and a `.dart` file are Running scripts), `git commit` (its pre-commit hook), `git push` (its pre-push hook, next to the push itself, which is Running scripts), and shell scripts called by path (`./scripts/test.sh`, `script/test`; only files with a shell shebang or extension are read as commands). When the file that defines a script can't be read, its name decides, by its first word (`build:test` is a build, `test-unit` a test run, `dev` and `deploy` Running scripts), tagged `by-name`. turbo, nx and lerna task names are read the same way. `clean` doesn't count next to other tasks.
   - **A package's executable run by its path** (`./node_modules/.bin/vitest run`) is that program: its shim isn't the project's script. `npm pack` is Build.
   - **A script awf can't read** (a Python or Node file, or a shell script that's gone) and a program run by its path (`./run`, `.build/release/app`) are Running scripts: the project's own scripts and binaries, doing something awf can't see into.
   - **fastlane lanes** (`fastlane <lane>`, `bundle exec fastlane ios <lane>`) are read from the Fastfile (`fastlane/Fastfile`) and classified by their actions, as a compound command: `scan` and `run_tests` are Running tests, `gym` and `build_app` Build, `swiftlint` Lint and format, `gradle(task: ...)` by its task, uploads and signing (`upload_to_testflight`, `deliver`, `match`) Running scripts, and the lanes a lane calls by theirs. A lane's `sh` steps count only when it has no action awf knows: they are set-up around the action (generating the project before `scan`). When the Fastfile can't be read or the lane has neither, its name decides, by its first word, the whole name or its last word (`checkout_tests` is a test run), tagged `by-name`; a name that says nothing leaves it to the `fastlane` rules (Running scripts). fastlane's own tools (`fastlane scan`, `fastlane gym`) aren't lanes.
   - **A repo's own rules come first.** A rule in the repo's `.awf/rules.yaml` that matches a command decides before awf reads what it runs: `{ phase: tests, program: test.sh }` makes `./scripts/test.sh` and `bash scripts/test.sh` Running tests whatever the script contains, and `{ phase: tests, match: '(^|/)scripts/e2e-.*\.sh' }` names scripts by path. The same holds for package scripts, make targets and task runners. Built-in rules never come first: awf reads the script. The rules are those of the repo the command runs in, found from its directory upward after any `cd`, so `cd ../ios && ./scripts/test.sh` from a session started elsewhere (a subagent in a worktree, say) follows the iOS repo's rules and failure patterns; a directory with no rules file of its own follows the session's.
4. **A failed check is detected from its exit code when the exit code is the check's own**: the check ends the command (`pnpm test`, `cd web && pnpm lint && pnpm test`). Then a passing run is a pass, even if its output contains a word like FAILED.
   - **When a pipe, `;`, `||` or `&` after the check hides its exit code** (`pnpm test | tail`, `pnpm test || true`), failure patterns in the rules file, matched against the output when the transcript has it, decide.
   - **When commands chained with `&&` follow the check** (`pnpm test && git commit -m x`), a pass is a pass; a failure may be the later command's, so the output decides when there is some, and otherwise the check is marked failed, tagged `failure-unattributed`.
   - In a compound command with several checks, a tool's own pattern says which check failed; without one, the highest-ranked check is marked failed, tagged `failure-unattributed`.
   - Each check is keyed by its tool and subcommand (`lint:cargo fmt`, `lint:cargo clippy`), so rework ends only when the same check passes.

## Overlaps and waiting

- When several things run at once (parallel calls, subagents), each instant goes to the highest-ranked phase among the calls running then, in the order Build, Running tests, Lint and format, Rework, Writing tests, Writing code, Running scripts, Exploring, Planning and answering, Waiting on you, Unclassified.
- Background work (a background shell, a Monitor or a subagent) only takes an instant when nothing in the foreground is running, so a build left running while you're away counts as Build, not Waiting on you.
- A background shell that is Running scripts or Unclassified (a dev server, a watcher, a poller) ranks below idle time: while you're away it's Waiting on you. Left running after the session's last step, it doesn't stretch the session. Inside a turn it still fills the gaps nothing else covers, like a request being resent. A Monitor ranks this way whatever its command runs, a `tail -F` (Exploring) too: it's a watcher by design. A background subagent running scripts while you're away is still working: that counts as Running scripts.
- A call that waited for your approval is split: the wait is Waiting on you, the run its own phase. With hooks, the run is `duration_ms`; from a transcript alone the wait's length is unknown, so the whole call counts as waiting.
- A call that reads a background task's output (TaskOutput, BashOutput) or stops it (TaskStop, KillShell) takes that task's phase: its background step's, from its command. For a Monitor, that's the phase of the command it runs, not the Monitor call's Running scripts.
- A background shell runs until its completion notice, or until a TaskStop or KillShell call stops it (a stopped task sends no notice). A Monitor's command runs the same way, from the Monitor call until its completion or kill notice, a TaskStop or KillShell, or its timeout, whichever comes first. Its events are notices too, without a status; they don't end it. With no notice, it ends at its timeout or at the transcript's last entry, whichever is first, flagged `unfinished`: Claude Code kills it when it exits.
- **A compaction while you're away is part of the wait.** Claude Code compacts a session left idle before its prompt cache expires, about 54 minutes after the last turn ("Compacted while idle"). It holds nothing up, so it isn't overhead like a compaction inside a turn: between turns it's Waiting on you, tagged `compaction`, inside the idle gap, and background work running then still takes its time. After the last turn it isn't part of the session and doesn't stretch it. If you send a prompt while it runs, the rest of it holds up your turn and is Unclassified. A `/compact` you typed is one you wait for: Unclassified, even between turns.
- **A request sent more than once isn't model time until the send that was answered.** After an API error, a timeout or a rate limit, Claude Code sends the same request again, sometimes for an hour, and the agent generates nothing in between. Model time starts at the send that was answered (the step is flagged `resent`). Before it, the agent's own background tasks take the time while they run (a build it started is Build), then the rules above apply: between turns it's idle time, Waiting on you; inside a turn with nothing else running, it's agent overhead, counted as Unclassified. The transcript records each send from Claude Code 2.1.300; older transcripts and the hooks can't tell a resend from a long answer.
- Only gaps between turns count as waiting: time before your first prompt and after the last turn isn't part of the session.
