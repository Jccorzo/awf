# Phases

Every instant of a session belongs to exactly one phase, so phase times add up to the session's total. Phases come from PLAN.md; don't add one without asking. The rules that decide them live in [src/classify/default-rules.yaml](../src/classify/default-rules.yaml), and a repo can extend them in `.awf/rules.yaml`.

| Phase                  | What counts                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Writing code           | Model time before an Edit or Write on a source file, plus the edit. Shell commands that write files (`mkdir`, `cp`, `mv`, `rm`, `sed -i`, output redirected to a file, `git add`/`commit` without hooks) count too                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

| Lint and format        | eslint, prettier, biome, ruff, black, isort, flake8, mypy, pyright, golangci-lint, gofmt, go vet, cargo clippy, cargo fmt, ktlint, detekt, swiftlint, swiftformat, dotnet format, `tsc --noEmit`, stylelint, shellcheck, rubocop                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Running tests          | jest, vitest, mocha, playwright test, pytest, go test, cargo test, gradle test, mvn test, dotnet test, xcodebuild test, swift test, bazel test, bun test, `node --test`, rspec, `cargo fuzz run`, cargo-mutants                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Build                  | tsc, vite build, webpack, esbuild, next build, go build, cargo build, gradle assemble, mvn package, dotnet build, msbuild, xcodebuild build, swift build, bazel build, make, cmake --build, docker build. Installing dependencies (`npm install`, `pip install`, `go mod download`, `bundle install`, `bundle lock`, `gem install`, ...) and creating a project (`create-next-app`) count as Build, tagged `install`. `cargo clean` is Build, like Gradle's `clean`                                                                                                                                                                                                                                                                                                                       |
| Rework                 | Code or test edits, and the model time before them, after a failed lint, test or build, until that same check passes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Exploring              | Read, Grep, Glob, web search and fetch, and the model time before them. ## Attribution rules

1. **Model time goes to the phase of the tool call it produced.** When one stretch of model time produced several calls (a batch), it takes the highest-ranked of their phases, in the order of "Overlaps and waiting" below: writing an edit outranks running a script, since the model's time went into the edit. Model time before a question to you, a subagent or nothing at all is Planning and answering.
2. **A compound command takes the highest-ranked phase**, in the order Build, Running tests, Lint and format, Running scripts, Writing tests, Writing code, Exploring. The other phases stay as tags. `npm run lint && npm test` is Running tests, tagged Lint and format. Commands that change nothing (`cd`, `echo`, `export`, `sleep`, `kill`, `true`, `open`) don't count; a command made only of them is Unclassified.
   - **Running something takes the time.** Edits and reads in a shell take next to no time, so in `mkdir -p out && python3 gen.py` the script most likely took it: the command is Running scripts, not Writing code. `python3 gen.py && pnpm test` is still Running tests.
   - **A part no rule matches** ranks above Running scripts, below the checks: it could be anything, so `python3 gen.py && frobnicate` is Unclassified.
   - **A filter after a pipe** (`| tail`, `| grep`, `| jq`) decides nothing unless it is a check or writes files: `pnpm test | tail` is Running tests, `some-cli | tail` is Unclassified.
   - **Polling** (a `sleep` inside a `while`/`until`/`for` loop, or a sleep of 5 seconds or more) is Running scripts, tagged `polling`, unless the command also runs a check: the time went to waiting for something outside the session, like CI, a deploy or a server starting. The summary says how much of Running scripts was polling.
   - Calls of shell functions defined in the same command (in a substitution too, and inside an `if`), and `case` patterns, are skipped; the function's body is counted once. An array's values (`ARGS=(-a "$b")`) aren't commands.
   - **A variable run as a command** (`G="git -C ../x"; $G status`, `"$CHROME" --headless`) runs what it was set to earlier in the same command. A value from a command substitution (`T=$(cat tool)`) isn't known.
   - **Commands inside a substitution count**: `OUT=$(pnpm test 2>&1); echo "$OUT" | tail` is Running tests, and so is `diff <(git show HEAD:a.ts) a.ts`'s `git show`. A `cd` inside parentheses ends with the subshell.
   - **Browser and computer-use calls** are classified by what they do, from the action names in their input. Looking at a page or the screen (`navigate`, a screenshot, `zoom`, scrolling, `get_page_text`, `find`, console and network logs) is Exploring; acting on it (clicks, typing, `javascript_tool`, `preview_start`) is Running scripts. A batch (`browser_batch`, computer use's `computer_batch`) takes the highest-ranked of its calls, so a batch that clicks is Running scripts and one that only loads a page and takes a screenshot is Exploring. Waiting for the page (`wait`) doesn't count next to other calls; a call that only waits is polling.
   - **Commands that run other commands** are classified by what they run: `find … -exec black {} +`, `run-s lint test`, `concurrently "npm:test"`, and task runners (`just test`, `task lint`, `mise run build`, `rake spec`, `composer test`) by the task's name.
3. **Scripts are resolved to what they actually run before classifying**: `npm run <script>` and its `pnpm`, `yarn` and `bun` forms (with their `pre` and `post` scripts), `make <target>` (the target's own recipe; an empty one runs its prerequisites), Gradle tasks and Maven goals (by task name), `git commit` (its pre-commit hook), `git push` (its pre-push hook, next to the push itself, which is Running scripts), and shell scripts called by path (`./scripts/test.sh`, `script/test`; only files with a shell shebang or extension are read as commands). When the file that defines a script can't be read, its name decides, by its first word (`build:test` is a build, `test-unit` a test run, `dev` and `deploy` Running scripts), tagged `by-name`. turbo, nx and lerna task names are read the same way. `clean` doesn't count next to other tasks.
   - **A script awf can't read** (a Python or Node file, or a shell script that's gone) and a program run by its path (`./run`, `.build/release/app`) are Running scripts: the project's own scripts and binaries, doing something awf can't see into.
   - **fastlane lanes** (`fastlane <lane>`, `bundle exec fastlane ios <lane>`) are read from the Fastfile (`fastlane/Fastfile`) and classified by their actions, as a compound command: `scan` and `run_tests` are Running tests, `gym` and `build_app` Build, `swiftlint` Lint and format, `gradle(task: ...)` by its task, uploads and signing (`upload_to_testflight`, `deliver`, `match`) Running scripts, and the lanes a lane calls by theirs. A lane's `sh` steps count only when it has no action awf knows: they are set-up around the action (generating the project before `scan`). When the Fastfile can't be read or the lane has neither, its name decides, by its first word, the whole name or its last word (`checkout_tests` is a test run), tagged `by-name`; a name that says nothing leaves it to the `fastlane` rules (Running scripts). fastlane's own tools (`fastlane scan`, `fastlane gym`) aren't lanes.
   - **A repo's own rules come first.** A rule in the repo's `.awf/rules.yaml` that matches a command decides before awf reads what it runs: `{ phase: tests, program: test.sh }` makes `./scripts/test.sh` and `bash scripts/test.sh` Running tests whatever the script contains, and `{ phase: tests, match: '(^|/)scripts/e2e-.*\.sh' }` names scripts by path. The same holds for package scripts, make targets and task runners. Built-in rules never come first: awf reads the script. The rules are those of the repo the command runs in, found from its directory upward after any `cd`, so `cd ../ios && ./scripts/test.sh` from a session started elsewhere (a subagent in a worktree, say) follows the iOS repo's rules and failure patterns; a directory with no rules file of its own follows the session's.
4. **A failed check is detected from its exit code when the exit code is the check's own**: the check ends the command (`pnpm test`, `cd web && pnpm lint && pnpm test`). Then a passing run is a pass, even if its output contains a word like FAILED.
   - **When a pipe, `;`, `||` or `&` after the check hides its exit code** (`pnpm test | tail`, `pnpm test || true`), failure patterns in the rules file, matched against the output when the transcript has it, decide.
   - **When commands chained with `&&` follow the check** (`pnpm test && git commit -m x`), a pass is a pass; a failure may be the later command's, so the output decides when there is some, and otherwise the check is marked failed, tagged `failure-unattributed`.
   - In a compound command with several checks, a tool's own pattern says which check failed; without one, the highest-ranked check is marked failed, tagged `failure-unattributed`.
   - Each check is keyed by its tool and subcommand (`lint:cargo fmt`, `lint:cargo clippy`), so rework ends only when the same check passes.

## Overlaps and waiting

- When several things run at once (parallel calls, subagents), each instant goes to the highest-ranked phase among the calls running then, in the order Build, Running tests, Lint and format, Rework, Writing tests, Writing code, Running scripts, Exploring, Planning and answering, Waiting on you, Unclassified.
- Background work (a background shell or subagent) only takes an instant when nothing in the foreground is running, so a build left running while you're away counts as Build, not Waiting on you.
- A background shell that is Running scripts or Unclassified (a dev server, a watcher, a poller) ranks below idle time: while you're away it's Waiting on you. Left running after the session's last step, it doesn't stretch the session. A background subagent running scripts while you're away is still working: that counts as Running scripts.
- A call that waited for your approval is split: the wait is Waiting on you, the run its own phase. With hooks, the run is `duration_ms`; from a transcript alone the wait's length is unknown, so the whole call counts as waiting.
- A call that reads a background task's output (TaskOutput, BashOutput) takes that task's phase.
- A background shell runs until its completion notice, or until a TaskStop or KillShell call stops it (a stopped task sends no notice).
- **A request sent more than once isn't model time until the send that was answered.** After an API error, a timeout or a rate limit, Claude Code sends the same request again, sometimes for an hour, and the agent generates nothing in between. Model time starts at the send that was answered (the step is flagged `resent`). Before it, the agent's own background tasks take the time while they run (a build it started is Build), then the rules above apply: between turns it's idle time, Waiting on you; inside a turn with nothing else running, it's agent overhead, counted as Unclassified. The transcript records each send from Claude Code 2.1.300; older transcripts and the hooks can't tell a resend from a long answer.
- Only gaps between turns count as waiting: time before your first prompt and after the last turn isn't part of the session.
